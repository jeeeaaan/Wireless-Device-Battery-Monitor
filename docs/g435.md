# Logitech G435 LIGHTSPEED battery support

## Device

| Connection | VID:PID | Interface | Usage page:usage | Input / output / feature |
|---|---|---|---|---|
| USB LIGHTSPEED receiver | `046D:0ACB` | 3 | `FFC0:0001` | 8 / 515 / 64 bytes |

The dongle's vendor collection (`FFC0:0001`, report 6) is not HID++, so the generic
Logitech HID++ driver cannot read it. The USB chip is a Realtek ALC4021; the radio SoC behind it
is an Audiowise/Airoha PAU1823. The bridge talks to the Realtek side and forwards "PA" commands to
the SoC.

## Captured frames

Command framing and replies (report ID `06`), from the protocol test and
[deddroid/logitech-g435-battery](https://github.com/deddroid/logitech-g435-battery):

```text
request:  50 41 <category> <seq> <len> <command...>
reply:    50 49 ...

REMOTE_GET_CONNECT_STATUS:  0e <seq> 01 e3  ->  02 00 e3 <0/1>   (plus 03 00 0e <seq|80> 00)
REMOTE_SET_MODE:            0e <seq> 02 e1 01 -> 03 00 0e <seq|80> 00
GET_BATTERY:                06 <seq> 01 00 31 -> 07 00 06 <seq|80> 00 <mV lo> <mV hi>
```

GET_BATTERY example reply captured from the `046d:0acb` dongle (4146 mV):

```text
06 50 49 01 C8 75 48 0D 00 07 00 06 82 00 32 10 00 00 FF FF FF FF
```

The low 7 bits of the reply's fourth byte (`82` here) are the sequence echoed back from the
request. Replies from a late or different command are rejected by matching that sequence.

## Read sequence

```text
06 01 03                         enter bootloader
PA 0e 01 01 e3                   connected?  0 -> headset off, stop
PA 06 02 01 00 31                battery     plausible -> done
PA 0e 03 02 e1 01                otherwise: remote mode 1
PA 06 04 01 00 31                battery again
06 08 03                         leave bootloader (always, also on error)
```

GET_BATTERY reaches the headset only in remote mode 1. In mode 0 the dongle answers it itself with
a small meaningless value (105 and 210 mV were seen), so anything outside 2500–4600 mV is treated as
"set mode 1 and ask again".

## Polling, cache and connection

GET_BATTERY stops audio and microphone for about 0.6 s (a dongle firmware limitation). The battery
value is therefore queried at most once every 15 minutes and cached **in memory only**. No state
file is written, so the first battery query after starting the application can briefly interrupt
audio.

The wireless `GET_CONNECT` query (0xE3) is cheap and runs on every poll. It updates the `connected`
flag as soon as the headset is switched off or disconnected, without waiting for the battery cache
to expire. When `connected == 0` the driver returns `connected = false` and no battery row is shown.

## Validation

`make test` builds and runs `tests/g435_protocol_test.cpp` (framing, parsing, sequence rejection,
voltage bounds, percent curve) and `tests/g435_driver_test.cpp` (simulated HID transport covering the
happy path, connect-only polling, stale-sequence rejection, timeouts, enter failure, and incomplete
or invalid battery replies).
